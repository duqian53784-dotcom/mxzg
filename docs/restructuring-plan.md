# mxzg 工程重整路线

以大陆简体中文 H5、App、微信小游戏的现代化重做版为目标。按新的产品体验和技术边界设计，现有工程与日服分别作为可复用成果和业务参考，不作为新架构模板。

架构方向已经确定为按功能组织的轻量 MVC 客户端与模块化单体后端，以人能阅读、修改和排错优先。具体分工、UIManager 契约与后端取舍见 [架构与维护指南](architecture.md)。

## 已启动的实现

backend 已建立独立 Java 21/Spring Boot 4.1.2 工程、Maven Wrapper、角色与会话数据库迁移，开发登录和角色查询可通过真实 HTTP 验证。local 使用独立 H2 文件库；正式 MySQL、渠道身份、新客户端登录 MVC 和战斗切片仍为接续工作。见 backend/README.md 的实际入口与测试命令。

## 第一阶段 定义新方案与复用边界

已经建立需求、问题清单、检查入口和静态依赖审计，完成两处明确的代码归位。上述工作记录旧工程基线，不代表继续以修补旧架构为主线。

接续：明确新手流程、主循环和页面导航；确定 app、platform、framework、net、features 的边界、数据所有权及新接口契约。对旧玩法、美术、代码、Prefab、配置和 Java 服务逐项决定直接复用、封装、改造或淘汰。

验收：有清晰的新方案、一条可实现的玩法切片与复用清单。当前检查和失败记录保留；旧页面坐标或完整修复全部历史债务不作为新方案开工条件。继续使用的资源保留 UUID，用户已有修改不被覆盖。

## 技术选择与复杂度控制

当前 Creator/TypeScript 作为先行验证方案，按三端构建、低端设备、资源加载、调试体验、SDK 接入和维护成本决定保留、升级或替换。先取得最小样包证据，再确定引擎和工具链版本；不因老项目年代久就无差别重写，也不因已经迁移大量资源就锁死技术。

服务端建立新的 Java/Spring Boot 模块化单体底座与 MySQL 持久化，首期单一游戏应用启动。旧 Java 的战斗、掉落与养成规则按新需求提取并验证，旧基础框架、接入与部署不直接继承。技术与版本基线见 architecture.md；独立服务和中间件按真实需求引入。

新接口表达业务动作，维护版本与可生成的类型定义。确需复用旧服时，由适配器转换旧协议，不让旧 opcode、字段号和静态会话渗入新 View 与规则模型。

## 第二阶段 提前验证多端样包

用新边界建立环境配置与 platform 服务契约：身份、支付、存储、生命周期、设备和网络，由组合根选择实现。SDK 未接入时标明开发替身。页面按重做版体验设计，不套用旧 CCBI 层级和固定坐标。

最小链路为启动、配置加载、登录、主城、断线与前后台恢复。H5、Android、微信小游戏在同阶段试跑；iOS 在 Apple 工具链环境验证。

验收：使用构建产物连接测试网关；微信真机和低端 Android 记录时间、流量、内存；业务不必读取浏览器 URL 参数才运行。

## 第三阶段 完成真实主循环

按登录/创角、英雄、出阵、主线、结算、挂机领取、基础养成、重登推进。先确定新业务契约与状态模型，再选择复用旧服务、边界适配或新增实现；复用旧写操作时确认版本与副作用。

每个 feature 拥有 Model、Controller、Service 与 View，规则和模型保持可独立测试。新 View 不直接读取全局 Store、监听 WireSession 或决定业务跳转；流程由 Controller 协调。旧服通过适配层接入，切换完成后删除旧状态和分支。

验收：每个写操作有真实请求、回包、服务端查询或重登证据，覆盖失败、重复点击与重连；Mock/JSON 对照库仅辅助开发。

## 第四阶段 替换旧实现并删除冗余

按新主循环的依赖推进功能，不要求逐个搬完旧系统。新路径通过业务、真实服务端与新设计验收后，替换对应旧入口，删除旧壳、回退开关、重复规则和失去用途的工具/测试。

统一导航、取消、订阅和资源释放；采用 Creator 时由 Prefab 绑定结构，列表用 Cell Prefab。新数据由唯一 store 所有，旧 Session/GameStore/会话快照通过切换退休，不在新架构继续复制。

验收：反复进入、快速切页、加载失败和返回正确；视觉与交互符合新设计；没有监听与资源累积；删除有完整引用检查。旧截图/坐标测试按明确的设计变更更新或淘汰，新验收必须同时补齐。

## 第五阶段 资源与发行

拆首屏、核心、战斗和扩展资源，按三端构建输出制定包体、下载、内存和加载预算；配置也按核心与功能加载。

接入大陆账号、支付、商品、公告、版本与运营配置，完成生产网关、日志监控、更新和回滚。发行资质及渠道要求由发行方案核实。

验收：三端发布包与真机证据；服务端支付校验、幂等与补单闭环；生产包无可用开发身份和 GM；版本可追溯。

## 代码归属

- app：组合根、启动与会话编排，不写养成规则。
- platform：统一契约和 H5/原生/微信实现，由 app 装配。
- framework：必要的通用 UI、资源与布局基础，不 import 业务页面，不为追求通用而堆叠框架。
- core：基础类型、错误、日志与通用工具；既有 Session/Store 逐步收敛，不继续堆系统。
- net：连接、帧、协议与兼容，不承载全部玩法状态。
- features/功能：Model、Controller、Service、View/Cell 及必要规则；优先功能内集中阅读，不机械拆分深层目录。
- module：现有规则的候选复用来源，按质量与新需求决定改造或删除；新业务不受其结构约束。
- ui：尚在运行的旧表现层，随新功能替换减少，不再新增业务大分支。
- 测试支持：Mock、回放、shim 最终只由测试/开发入口装配。

阶段顺序表达依赖关系，不是工期承诺。现代化按体验、边界、验证与维护成本衡量；不以目录重命名、重写比例或技术数量衡量。

## 本地检查

Python 3、Node.js 可用后，在 client 安装固定版本开发依赖并运行 `npm run check`，或从根目录运行 `node client/tools/check-project.mjs`。离线时可设置 `MXZG_ESBUILD_MODULE` 为已安装 esbuild 模块路径，`MXZG_PYTHON` 可指定 Python。

- 单项：`node client/tools/check-project.mjs --suite architecture`。可选 architecture、bindings、backpack、hero、city、battle、legacy。
- 审计：`python tools/project_audit.py --json`。
- 日志与结果：`client/temp/project-checks/`，属于本机临时文件。

入口覆盖静态依赖、脚本绑定、esbuild 打包和无引擎行为；不等同于完整 TypeScript 类型检查、Creator 构建、真服持久化或三端实机验收。
