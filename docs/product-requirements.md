# mxzg 大陆多端产品需求

本项目是面向中国大陆的现代化重做版，以简体中文发布 H5、App 和微信小游戏。三个终端共用玩法、角色数据和主要界面；账号、支付、生命周期、缓存与更新通过平台适配层处理。用户指定的核心流程以日服正式服的视觉、交互和规则为对照目标；重做架构不等于重新决定这些流程的产品设计。必要差异单独记录，未核实或未实现的内容明确标注，不能自行当作已接受的改版。

确认日期：2026-10-29；2026-10-30 按用户新要求校正本批优先级。地区、语言和微信小游戏形态已经确认；App 暂按 Android/iOS 规划，首发商店及先后顺序待定。资质、实名、防沉迷、隐私和渠道支付等发行事项由发行方案确认，客户端能构建不能代替上线准备。

## 当前批次的范围与开发顺序

三端骨架仍是前期目标；当前批次只完善既有背包 MVC 的四类库存事件、状态通知及必要业务/UI 调用。Model 校验整批数据、计算并一次性提交后返回只读变化清单，Controller 聚合细分并最终汇总；首次/会话清理不当获得/消耗，未知原因不猜测，回调不能中途提交下一批。BagView 只用汇总刷新列表，状态另行更新提示。事件不得代替真实领奖结果来推断奖励动画。不扩展其他模块或玩法；出阵/列表的人工体验仍待用户确认。

2026-10-30 最新要求：后续不再构建 H5 或其他任何包，等用户需要时再执行；日常开发与本批验收以本机 Creator 预览为主。保留已有独立 H5 通过证据，但不能拿旧产物或本机预览冒充当前源码的包验收。上一批取消的默认布局 H5 构建不计作成功发布。

客户端新标准统一为完整名称的模块级 MVC：BagController 继承 BaseController、BagModel 继承 BaseModel、BagView 继承 BaseView；全局 EventDispatcher 与 EventScope 统一通知和监听清理。Controller 处理请求/回包与操作，Model 保存唯一角色状态并提供只读查询，View 打开先监听再读 Model、关闭只解除自身订阅，Prefab 保存静态配置。Controller/Model 独立于窗口；换号/换服/退出使旧请求失效；先提交全部相关状态再发有类型事件。旧的强制 Service/Presenter/Presentation 客户端层次要求已被替代，现有未迁移模块列入后续批次，不作为并行标准。具体实施见 [架构指南](architecture.md) 与 [背包维护指南](bag-mvc-maintenance.md)。

背包列表使用原生 ScrollView/Layout 的薄扩展，布局与 Cell Prefab 只在 Inspector 维护，业务传递类型明确的数据和渲染回调；同分类刷新保留滚动位置，分类切换回到起点。等尺寸 Cell 为第一版范围，虚拟列表以实际数据量与性能证据决定，不默认扩展。

用户的日常开发流程固定为：明确需求 → 约定后端协议 → 生成前端接口与类型 → 制作 Prefab → View 绑定展示 → 编写业务逻辑。功能必须提供可定位的修改入口，不以只有 AI 能追踪的隐式规则维护。当前阵容接口仍使用已有手写 DTO/请求适配；本批没有新增后端协议，也不把接口生成能力标为已经完成。后续新增功能在协议和生成方式明确前不先堆业务 UI。

技术检查、实际运行检查和人工修改体验分别验收。只有用户亲手在 Creator 修改、保存、预览并确认好用后，才能把样板的“人工可维护体验”标为验收通过；AI 的序列化探针、截图和自动化检查不能代替用户确认。

## 重做版的设计原则

- 人能阅读、在编辑器修改 UI、追踪业务和独立排错是首要标准。客户端采用按功能组织的轻量 MVC，UIManager 统一界面生命周期；后端采用新的 Java/Spring Boot 模块化单体底座，按需验证并提取旧规则。具体职责、维护入口与后端取舍见 [架构与维护指南](architecture.md)。
- 根据当前三端能力、长期维护成本、工具链和团队可控性选择技术。现有 Creator/TypeScript 是待验证的候选基础，3.8.8 是当前版本事实，不是永久技术约束；更换或升级需要样包证据。
- 指定核心流程包括加载与登录、选区选服、主城、英雄、背包、挂机、出阵、主线战斗、结算与返回挂机。其构图、控件比例、切换反馈和规则以正式服为对照；简体中文、平台适配和必要技术差异单列说明。不得用“现代化”擅自替换核心布局、跳过步骤或改变玩法规则；开发联调壳、占位值和缺失功能不能当作最终方案。
- 未列入首测的系统可按产品价值排期；已指定的核心流程不能因为重做而自行简化。旧项目存在某个非核心系统，不构成新版本必须立即实现的理由。
- 新客户端按功能组织，明确数据所有权、业务服务和平台边界；优先简单可维护的实现，不为“现代化”堆叠框架、全局事件或分布式系统。
- 服务端、接口和配置重新评估。旧 Java 业务可复用、封装或替换；旧协议只在需要兼容时通过边界适配，新业务接口使用明确、版本化、可生成类型的契约。
- 现有迁移成果逐项评估：质量与新需求一致的保留，边界清晰的改造，过时壳层与重复路径替换或删除。重做不以清空仓库为起点，也不以修好全部旧实现为前置条件。

历史代码和迁移脚本不约束新工程架构；指定核心流程的正式服对照目标仍然有效。差异应区分已确认的本地化/平台差异、暂未实现的缺口和待用户确认的设计变更，不把技术现状自动解释成已确认需求。

## 核心玩家需求

### 账号与角色

- 平台凭据经服务端验证后换取游戏会话。手输数字 uid、客户端派生 uid 和本机 GM 只用于开发。
- 明确统一账号、渠道身份与区服角色的映射。同一账号在允许互通的终端上读取同一角色；微信与 App/H5 的账号绑定规则在接 SDK 前确定，不能默认自动互通。
- 支持公告、选服、创角、登录、断线重连、切换账号，以及前后台恢复后的重新同步。
- 维护、超时、鉴权失败、版本不兼容有明确状态和恢复路径，不能进入旧角色或伪造新手数据。

### 首个可玩的主循环

1. 新账号登录、创角、进入主城。
2. 获得英雄、查看技能、确认出阵，并由服务端保存。
3. 挑战当前主线、播放战报、结算，刷新角色、关卡和背包。
4. 挂机累积收益并领取，重登结果仍与服务端一致。
5. 使用基础道具、升级英雄，消耗和收益以服务端回包为准。
6. 退出、重登或换终端后，阵容、英雄、物品和关卡保持一致。

主城、英雄、背包、主线/挂机、基础召唤、基础养成、基础邮件组成首个功能闭环。复杂活动、跨服、公会和高级养成按依赖与运营需求排期；未完成系统通过能力清单隐藏或展示明确开放条件。

### 商业发行能力

可玩的测试版本与可收费发行版本分别验收。收费发行还需：

- 渠道登录、有效会话校验、明确的人民币商品目录和价格来源。
- 服务端创建订单、验证渠道支付、幂等发货、查询和补单。客户端支付回调不能直接发货。
- 公告、邮件、维护、开服、运营配置、封禁与可追溯操作记录。
- 客户端、协议和资源版本兼容策略，更新失败的恢复与回滚。
- 登录失败、支付失败、卡加载和战斗异常的日志与监控。

## 三端共同工程要求

- 业务通过统一接口调用登录、支付、存储、网络、生命周期、设备与安全区能力。
- development、staging、production 独立配置网关、资源地址、渠道与调试能力。线上连接不能依赖浏览器 URL 参数。
- 服务端是角色、物品、货币、阵容和关卡的最终事实来源。未同步、空列表、零值和失败分别表达。
- GM、协议探针、Mock 和回放与玩家入口分离。生产构建与服务端均限制调试能力，不能只隐藏按钮。
- 使用当前 Creator 候选方案时，Prefab 管结构与布局，View 管绑定与展示，Controller 管交互流程，Model 管状态，Service 管接口用例；UIManager 统一打开、取消、返回与销毁。职责边界不依赖最终引擎选择。
- 中文文案、图中文字、策划配置、公告和价格采用大陆基线。日服覆盖层只作参考，不能整套复制商品和渠道行为。

## H5 要求

- HTTPS 页面、可配置的安全网络入口，覆盖手机浏览器及微信内浏览器的触摸、音频启动与前后台恢复。
- 版本化资源和缓存失效策略，发布切换不能混用两版配置或脚本。
- 本机 PowerShell WebSocket 桥只用于开发。正式网关独立部署并验证连接容量、超时和访问控制。
- 发布构建验证浏览器兼容性、窄屏安全区、横竖屏策略与断网恢复。

## App 要求

- Android/iOS 共用游戏核心，原生 SDK 通过适配层提供登录、支付和设备能力。
- 分别维护包标识、签名、渠道、版本和构建环境；iOS 在具备 Apple 工具链的环境构建与验证。
- 商店升级、原生包更新与资源更新各有策略，下载进度条不等于已安装热更新。
- 验证返回键、暂停/恢复、失焦、权限和网络变化；使用引擎/平台存储，不能假定浏览器全局对象存在。

## 微信小游戏要求

- 使用选定引擎的微信小游戏目标构建，在微信开发者工具和真机运行；当前先验证 Creator 候选方案。
- 适配微信身份、网络、存储、生命周期及所需支付；引擎已有适配和自建薄适配均以实包验证为准。
- 明确首包、启动场景、分包、远程资源、缓存与过期资源清理，按当前平台要求验收。
- 不依赖远程可执行脚本，不能照搬日服 WASM 网页的覆盖脚本与更新办法。

Creator 支持小游戏和原生发布，仍须配置各平台工程与能力。参考官方[微信小游戏发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)、[原生平台发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/native-options.html)和 [Asset Bundle](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)。具体包体限制和发行要求在提审前重新核对。

## 完成标准

功能从“资产存在”依次经过“界面绑定、真实读取、真实写入、服务端持久化、异常恢复、三端验证”。只读或 Mock 不能标为完整功能。

核心操作记录对应请求、回包、状态更新与重登结果；扣费和奖励增加重复点击、超时重试和失败检查。指定核心流程按正式服的视觉、交互和规则对照验收，记录视口、页签、动画时刻及账号数据差异；无法同账号时不伪造等级、英雄或战力来凑图。必要差异逐项说明，不能据单张截图或类型检查宣称已达到 1:1。

性能记录首屏可交互耗时、首屏下载量、峰值内存、战斗帧率和反复切页的内存趋势。先确定低端设备与网络条件，测量后制定数值门槛。源资源大小不等于包体、首屏下载量或内存占用。

## 尚需落定的发行决策

- App 是否同时首发 Android/iOS，以及商店和渠道 SDK。
- 新服务端与配置的技术基线，以及旧 Java 服务能力、数据和协议的复用范围。
- 三端账号互通、绑定和区服规则。
- 首测功能、商品方案和发行接入负责人。

这些决策不阻塞边界整理和多端最小样包；正式账号与支付接入前必须落定。
